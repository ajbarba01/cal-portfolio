## What this is

`calbarba.com` for **Cal**'s unofficial dog-walking / house-sitting business. Two products in one:

- **Portfolio** — About, Services & Booking, Gallery, Reviews, Resources.
- **Self-serve scheduling** — clients see availability, book, manage an account, complete the reusable intake profiles, and see what they owe; quotes adjust by distance. Prepay is real but ships behind a kill-switch (see **Payments kill-switch**).

Goal: Cal redirects clients here, saves both sides time. Budget slim — hosting only (domain owned).

## MVP scope

**In:** availability + booking (Cal sets slots; clients see open/booked; book a service; hour/lead-time rules); accounts + forms (profile, pets [name/species/breed/birthdate/optional photo], the reusable intake profiles, first-time onboarding gate); Stripe prepay behind its kill-switch; haversine auto-quoting.
**Reframed:** sliding scale → informational section on Services & Booking, not its own feature.
**Deferred:** SMS reminders (Twilio), Google Calendar sync (Cal wants manual control), Mapbox drive-time accuracy.

## Distance pricing (zero ongoing cost)

One geocoded location feeds **four** decisions: whether an address is servable at all, whether a booking needs Cal's approval, what the travel line costs, and how much calendar time a trip reserves.

- Cal's **origin is a configurable setting** (Boulder / Springs / etc) — a row Cal edits.
- **Geocode each client once** when the address is saved: ZIP → lat/lng from a free bundled US ZIP-centroid dataset (offline) or one free geocode call. Store `lat`/`lng`. Geocoding is a **vendor adapter** in `features/pricing/`, swappable for a real geocoder later (ENGINEERING #4).
- **Pipeline:** pure `lib/haversine.ts` (miles, math only — ENGINEERING #2) → × `road_factor` for road miles, and ÷ `avg_speed_mph` for **estimated one-way driving minutes**. All Cal-tunable; the whole estimate is one module, swappable for Mapbox drive-time later. No per-booking API call, no recurring cost.
- **Service-area gate (address save).** The booking-time gate alone is too late and too weak — an unplaceable ZIP reads as "unknown location", which means permanent manual approval rather than a refusal, so someone three states away could sign up and wait for a meet & greet Cal was never going to accept. `checkZipServiceArea` therefore runs when the address is entered, and refuses both a ZIP past the cutoff and a ZIP the geocoder cannot place at all. A client saving their own address gets an inline field error; admin creating a client on their behalf is **warned, not blocked** (the same warn-don't-block rule the admin booking surfaces follow).
- **Approval gate (miles, not minutes).** Distance-based, as Cal reasons: straight-line haversine `miles` > `auto_approve_threshold_miles` (~8 mi) → manual approval; > `hard_cutoff_miles` (~50 mi) → refuse. `gate_use_road_miles` flag (default off) switches the gate to `miles × road_factor` (real driving distance) — no rewrite. Both thresholds are Cal-tunable values, not code.
- **Travel cost — per road mile, not per minute.** The quote engine bills **one-way road miles** (`haversine × road_factor`) through a per-service travel modifier that grants a free allowance and then charges per mile beyond it. Every service type carries one, house-sitting included; whether it bills, how many miles are free, and the per-mile rate are all in that service's `pricing_config`. An unknown client location yields no miles, so no travel line.
- **Drive buffer (calendar, not price).** The driving-minutes estimate reserves scheduling room **before and after** every time-based booking — one-way drive time scaled by `drive_buffer_pct` — so back-to-back jobs can't be booked across town. A client with no coordinates buffers zero and routes to manual approval instead. Same distance input, a different consumer, and the only one that still uses minutes.

## Route map

Next.js App Router, three top-level route groups: `(auth)`, `(onboarding)`, and `(site)`, with `(marketing)`, `(account)` and `(admin)` nested inside `(site)`. The **Group** column below names whichever of those six a route sits in. `(onboarding)` is top-level on purpose — the gate below has to be able to send an un-approved client somewhere the account zone's own guard does not then bounce them out of. Auth-session refresh **and** the auth + onboarding gate live in middleware (`src/proxy.ts` → `src/lib/supabase/proxy.ts`). The **decision** is a pure function of its own (`src/lib/supabase/onboarding-redirect.ts`: `isGatedPath` + `onboardingRedirect`), unit-testable without a request or a session; the middleware is only the IO around it — read the profile, apply the answer, carry the refreshed auth cookies onto the redirect. Un-approved users are confined to `/onboarding`; approved users never see it. A **failed** status read is neither: middleware logs it and lets the request through rather than bouncing an approved client on a transient database failure, and the account-zone layout renders the shared `ErrorState` in place of the nav. Group layouts therefore keep a thin auth backstop **plus** that error surface. `role` guards sit at group layouts. Architecture rules in [ENGINEERING.md](ENGINEERING.md).

Full in-app admin so Cal never touches the Supabase dashboard.

**`/admin/availability` is paint-only.** It uses the `<Scheduler>` family (ADMIN capabilities preset) to manage when Cal is bookable, and it does **not** moderate bookings — a booked day is an ordinary selectable day and its booking renders on the timeline for awareness. Cal picks one day **or a run of them** (drag, shift-click, ctrl/cmd-click, or the keyboard), then paints walk windows on the timeline and flips overnight and premium across the whole selection; a toggle reads on only when every selected day is on. **Scope is the selection** for creates and toggles, because each of those is already a batch write. Carving time back out stays a one-day job — a removal can strand a booking and pops its own confirm — so the painter withholds the eraser and the block gestures while several days are selected. Painting booked time unavailable (or turning off an overnight night under a stay) is destructive, so the removal path intercepts the affected bookings, confirms each at a full Cal-initiated refund, and cancels them before applying the block. Writes do **not** go through `router.refresh()`: each server action `revalidatePath`s the route, so the RSC data refreshes inside the same transition, and the callbacks return the action's real result so a refused move reverts rather than snapping back silently.

Booking moderation — approve, decline, cancel — lives on `/admin/bookings` and the client detail page.

**Booking flow + deferred-auth gate.** `/services` is the public chooser hub; each active service card opens `/book/[serviceSlug]`, where the `<Scheduler>` family (BOOKING capabilities preset) drives selection — **month-range** (check-in/out dates) for house-sitting, **month→day-timeline** (`week-slots` mode) for hourly services: month picks the day, then a duration-accurate single-day timeline picks/types the start time. Live receipt auto-updates as selection changes (no "Get quote" button). Anyone may browse + pick; sign-in deferred to the **Book action**. A guest who clicks Book → `/login?returnTo=…`, a signed-in-but-un-onboarded user → `/onboarding?returnTo=…`; on success they land back on their exact selection. `returnTo` encodes the selection (slug in path; resolved start/end ISO + assigned pet ids in query), validated by a same-origin open-redirect guard (relative, must start `/book/`). `createBooking` keeps its own server-side `redirect("/login")` backstop. Every paid service is pet-aware and assigns **real pets** from the profile; per-species counts are derived server-side from the assignment, never typed in.

**Known limitation, accepted for now:** the round trip survives the hops the book page itself initiates, but not one the middleware gate makes. That redirect rebuilds the URL to carry refreshed auth cookies and clears the query string with it, so a user bounced by middleware — rather than by the book page's own gate — arrives at `/onboarding` or `/account` without their selection and re-picks it. Carrying the validated `returnTo` across that hop is a one-line change whenever it is worth making.

Shared booking-form leaf components (`PetAssignment`, `QuantityForm`, `QuotePanel`) live in `src/features/booking/_components/`, consumed by the book flow, the account self-edit route, and the admin on-behalf surfaces.

**Onboarding gate (meet & greet).** Booking gated on `profiles.onboarding_status` (see Data model). `createBookingCore` is the authoritative server-side gate: `approved` client may book any active service; `meet_greet_pending` may book **only** the free `meet-greet` service (one at a time); `info_pending` / `declined` book nothing — blocked submits return `onboarding_incomplete`. Book page mirrors this with per-state panels (`needs-info` / `needs-meet-greet` / `declined`). New clients finish the intro form (→ `meet_greet_pending`), book + attend an in-person meet & greet; Cal then **manually approves** from `/admin/clients/[id]` (any-direction override; confirm warns if approving before the visit's scheduled time).

## Data model

Supabase Postgres. Auth via Supabase `auth.users` (username / password **not** app columns). `client_id` = `auth.uid()`; Cal is `role='admin'`. Money = integer **cents**. RLS deny-by-default. Core logic (distance, quote, availability-overlap, booking state) lives in `features/*` as **pure functions**, IO at the edges ([ENGINEERING.md](ENGINEERING.md) #5); vendors (Stripe, geocoding) behind adapters (#4).

**Tables** (column → purpose):

- **`profiles`** (1:1 `auth.users`) — `id` (=auth.uid) · `full_name` · `email` · `phone` · `avatar_url` (single now; gallery later) · `address`, `zip` · `lat`, `lng` (geocoded when the address is saved, and gated by the service area then) · `kiche_allowed` (**deprecated** — retained, never read by pricing, no admin toggle) · `onboarding_status` (enum `info_pending` → `meet_greet_pending` → `approved`, plus `declined`; the booking gate = `approved`. `info_pending` finishing the intro form advances to `meet_greet_pending`; `approved` / `declined` are **admin-set** by Cal after the in-person meet & greet, any-direction override. Replaces the former `onboarding_complete` boolean) · `role` ('client' \| 'admin') · `created_at` · `unclaimed` (bool, default false — Cal-created shadow account not yet claimed; password-login impossible, notifications suppressed) · `claimed_at` (when the client set a password) · `invited_at` (when Cal last generated a claim link). See **Pre-created (unclaimed) clients** below.
- **`pets`** (was `dogs`) — `id` · `client_id`→profiles · `name` · `species` ('dog' \| 'cat' \| 'bird' \| 'rodent' \| 'reptile' \| 'fish' \| 'other'; canonical taxonomy in `src/features/pets/species.ts`, the single source of truth re-exported by pricing) · `breed` · `photo_url` (optional; object path in the private `pet-photos` storage bucket, served via short-lived signed URLs — written by the server, not by the client grant) · `notes` · `birthdate` (a column because pricing reads it: the puppy modifiers fire on a dog under six months at the stay start) · `created_at`. Rich per-pet medical / behavior / feeding narrative lives in a pet-scoped `form_responses` row (`pet_care`), not wide columns here. An earlier set of identity columns (`age`, `sex`, `weight`, `vet_*`, …) was **dropped**: the intake shipped as a form payload instead, so nothing ever wrote them, and vet contact belongs to the `owner` form.
- **`booking_pets`** — join (`booking_id`→bookings, `pet_id`→pets, PK both). Which specific pets are on a booking. Written by service role at booking creation; clients read their own. Pricing derives counts from assigned pets, snapshots into `quote_inputs`.
- **`services`** — `id` · `slug` · `name` · `description` · `pricing_type` ('house_sitting' \| 'check_in' \| 'walk' \| 'training') · `pricing_config` (jsonb `{ modifiers, constraints }`, Zod-validated — the source of truth for this service's rates and booking limits) · `default_duration_min` · `max_pets` (legacy capacity column; the live cap is `constraints.maxDogs` inside `pricing_config`) · `concurrency` ('exclusive' \| 'resident' — house-sitting = resident) · `form_key` (nullable; **vestigial** — still selected onto the service row, but the requirement manifest below decides which forms a booking needs) · `requires_approval` (force manual review) · `active` · `sort_order`. See **Pricing model** below.
- **`availability_windows`** — `id` · `starts_at` · `ends_at` · `note`. **Sole source of truth for when Cal is bookable** (#10); default world **closed**, Cal adds open windows. A booking must fall inside an open window _and_ within `settings.booking_open_minute..close_minute` (hard hours-of-day guard, **start and end**) and respect `min_lead_time_hours`; advance beyond `auto_confirm_horizon_days` is **pending, not refused** (only `hard_max_advance_days` refuses — see Booking state machine / Recurrence). Block-out = delete/trim a window (confirm + cancel any booking inside). Window recurrence deferred — one-off windows for MVP.

  **Live updates (what is published, and what is not).** Three tables are in the `supabase_realtime` publication. `availability_windows` and `overnight_nights` carry a window or night Cal changes straight to an open `/book/[serviceSlug]`; both are anon-readable, so the realtime authorization check passes for every viewer and nothing private is broadcast. `profiles` carries the approval that releases the onboarding wizard, and there the authorization check is what keeps it safe: the self-read policy makes only the subscriber's own row visible, so a client is streamed their own `onboarding_status` and no one else's. **`bookings` is deliberately excluded** — its rows carry client identity, and the public calendar reads busy ranges through a narrowed server action instead. Another client's booking therefore reaches an open calendar only through a **five-minute poll**, which pauses while the tab is hidden and refreshes at once on return. Events over polling where the data can be published (ENGINEERING #12); a bounded poll where it cannot.

- **`overnight_nights`** — `night` (date PK, Denver calendar; night D = Cal sleeps D → D+1) · `note` · `created_at`. Explicit per-night overnight availability for house-sitting. Admin toggles nights on/off; un-toggling a night with an active resident booking is refused (conflict returned, nothing cancelled). Public-read; all writes via service role / admin actions.
- **`settings`** (single config row Cal edits) — `origin_label` · `origin_lat`, `origin_lng` (current base; swappable Boulder / Springs) · `road_factor` (~1.3), `avg_speed_mph` (miles → driving-minutes; **travel-cost only**) · `auto_approve_threshold_miles` (~8), `hard_cutoff_miles` (~50, refuse beyond), `gate_use_road_miles` (bool, default false — gate on `miles × road_factor` instead of straight-line) — **distance approval gate, see Distance pricing** · `booking_open_minute`, `booking_close_minute` (minutes-since-midnight, hard hours-of-day guard; 390 = 6:30am, 1320 = 10:00pm; bounds **both** booking start ≥ open and end ≤ close — see `availability_windows`) · `min_lead_time_hours` · `auto_confirm_horizon_days` (~30 — within → auto-confirm; beyond → `pending_approval`), `hard_max_advance_days` (~365 — sanity outer cap, refuse beyond) · `recurrence_generation_horizon_days` (~42 — how far ahead open-ended series rows are materialized) · `recurring_min_occurrences` · `holiday_dates` (Cal-managed list of premium day-keys) · `drive_buffer_pct` (percent of one-way drive time reserved around a booking) · `reminder_lead_hours` (~24 — email fires this long before a confirmed start) · `cancellation_full_refund_hours` (~48), `late_cancel_refund_pct` (~50) — **cancellation/refund policy, see Booking state machine**. Everything here is Cal-tunable — values, not code.

  Three columns disagree with the settings form one way or the other, and are called out so nobody reads the form as the truth. **`recurring_discount_pct`** and **`holiday_surcharge_cents`** no longer feed pricing — both rates now live as modifiers in each service's `pricing_config` — so their fields were removed from `/admin/settings` and from the update schema while the columns (and the row-read schema) stay, dormant, awaiting a migration. **`no_show_charge_pct`** is absent from the form for the opposite reason — the field was deliberately removed while the column keeps a real reader, because the cancellation preview and the no-show core still size the debit from it (see Booking state machine). _(The whole row also supersedes the earlier minutes-based gate columns `auto_approve_threshold_min` / `hard_cutoff_min` and the integer `booking_open_hour` / `booking_close_hour` / `max_advance_days`.)_

- **`bookings`** — `id` · `client_id` · `service_id` · `starts_at`, `ends_at` · `series_id` (nullable FK → `booking_series`; groups a recurring set) · `comments` · `status` (state machine, below) · `payment_status` ('unpaid' \| 'paid' \| 'partially_refunded' \| 'refunded') · `distance_miles` (snapshot at quote) · `quote_inputs` (jsonb — pet counts, nights/partial, add-ons, holiday days captured at quote time) · `quote_breakdown` (jsonb — itemized result) · `discount_cents` (**vestigial, always 0** — every discount is a line in `quote_breakdown` and is already reflected in `final_cents`; nothing reads this column) · `final_cents` · `requires_approval` (derived) · `reminder_sent_at` (nullable) · `created_at`, `updated_at`. Amount owed = `final_cents` − **net** paid, where net paid is captured money minus everything refunded (`netPaid`, clamped at zero) — summing gross payments over-counts after a partial refund, so every "how much has been paid" question routes through that one function. `payment_status` is a **derived projection** of `payments` (single writer = Stripe webhook), never written independently (#10). No two **same-concurrency-class** bookings (`services.concurrency`) may overlap while active — enforced by a **Postgres exclusion constraint** (btree_gist over `tstzrange`, partitioned by class), not app code (ENGINEERING #11); cross-class (house-sit + short service) may overlap. Recurrence engine general (Google-Calendar-style); MVP exposes **weekly** only.
- **`form_responses`** — **entity-scoped** reusable intake profiles. `id` · `client_id` · `form_key` (five active keys: `owner`, `home_access`, `home_sitting`, `pet_care`, `pet_walk`; legacy `emergency` kept registered so old rows still validate but is no longer a required profile; legacy `home`/`pet` keys retired) · `pet_id` (nullable FK→pets `on delete cascade`; set only for pet-scoped rows: `pet_care`, `pet_walk`) · `booking_id` (nullable) · `data` (jsonb) · `submitted_at` (bumped on every submit **and** on a "Confirm up to date" action — drives staleness). Uniqueness is scope-aware: `(client_id, form_key, coalesce(pet_id, nil-uuid))`, so account profiles are one-per-client and pet profiles one-per-pet. The `scope` ('account' \| 'pet') + Zod schema per `form_key` live in `src/features/accounts/form-registry.ts` (code, validated at the edge — YAGNI, [ENGINEERING.md](ENGINEERING.md) #9). `owner` = identity/pronouns/backup/emergency contacts (account-scoped); `home_access` = door codes/alarms/wifi/parking (account-scoped); `home_sitting` = sleeping arrangements/house rules/guest policy (account-scoped); `pet_care` = medical/behavior/feeding (per-pet); `pet_walk` = route/leash/off-leash (per-pet, **dog-only** — species-gated in the requirement manifest). Bookings **require and confirm** these rather than re-collecting — see Booking requirement gate.
- **`authorizations`** — **append-only** audit trail for click-to-accept e-signatures (the Owner form's emergency-expense authorization). `id` · `client_id` · `kind` ('expense_auth') · `version` (the accepted text version) · `accepted_name` (typed legal name) · `accepted_at`. Each acceptance is a new immutable row; the booking/profile gate re-prompts only when the current `EXPENSE_AUTH_VERSION` is newer than the client's latest accepted row. Granted `select, insert` only (no update/delete) to `authenticated`.
- **`payments`** — `id` · `booking_id` · `client_id` · `stripe_payment_intent_id` · `amount_cents` · `currency` · `status` ('requires_payment' \| 'succeeded' \| 'refunded' \| 'failed') · `refunded_cents` (cumulative, cents) · `disputed_at` · `dispute_status` · `created_at`. Stripe behind `features/payments/` adapter.
- **`reviews`** — `id` · `client_id` (null for imported) · `author_name` (snapshot) · `rating` (1–5) · `body` · `status` ('pending' \| 'published' \| 'rejected'; `pending` remains in the enum for legacy rows only) · `source` ('native' \| 'rover') · `external_key` (stable id for imported rows, null for native) · `created_at`. **Native** reviews are client-submitted, **auto-published** (maintainer decision 2026-06-11); Cal moderates reactively (reject/unpublish via admin reviews). **Rover** reviews are imported testimonials with no account: edit `src/content/rover-reviews.ts`, then `npm run rover:sync` (local) / `rover:sync:prod` reconciles them by `external_key`. Only the service-role sync script can mint them (RLS insert requires `client_id = auth.uid()`); on `/reviews` they share the card shell with a tint + "View on Rover" link (single site-wide URL).
- **`inquiries`** — public contact-form submissions. `id` · `client_id` (nullable FK→profiles; null = guest, set = signed-in submitter) · `name` · `email` · `phone` (nullable) · `subject` (nullable) · `message` · `status` ('new' \| 'resolved') · `replied_at` (nullable; stamped when Cal opens an email/SMS reply — a timestamp, not a state) · `resolved_at` (nullable) · `created_at`. RLS: **no public insert** — submissions flow only through the service-role `submitInquiry` server action (honeypot + per-email rate-limit + Zod), so callers can't forge `client_id`/`status`/timestamps or bypass guards via the REST API; owner/admin read, admin update.
- **`booking_series`** — durable rule for a weekly recurrence (so open-ended "no end" series materialize forward by a cron instead of inserting infinite rows up front). `id` · `client_id` · `service_id` · `freq` ('weekly') · `step_interval` (the rule's interval; `interval` is a Postgres keyword) · `count` (nullable) · `until` (nullable) · `open_ended` (bool — true ⇒ neither `count` nor `until`) · `template_starts_at` · `duration_min` · `quote_inputs` (jsonb — **frozen** at submit so every occurrence re-quotes identically) · `skipped_starts` (timestamptz[] — RFC 5545 EXDATE; cadence starts removed by an occurrence edit so the roll cron never refills them) · `active` · `created_at`. `bookings.series_id` FKs here. See **Recurrence** below.
- **`client_debits`** — outstanding balances that gate re-booking. `id` · `client_id` · `booking_id` · `amount_cents` · `reason` ('late_cancel' \| 'no_show') · `settled_at` (nullable) · `resolution` (nullable 'paid' \| 'waived' \| 'adjusted' — **how** it was cleared, for Cal's own reporting; the balance projection ignores it and still keys off `settled_at is null`) · `created_at`. Outstanding balance = Σ `amount_cents` where `settled_at is null`; positive balance **blocks new bookings** (see Booking state machine, cancellation/refund). **System/admin-set, never client-writable** (same column-guard rule as `bookings.status`).

**RLS approach (deny-by-default):**

- Per-client tables (`profiles`, `pets`, `bookings`, `form_responses`, `payments`): row readable/writable only when `client_id = auth.uid()`. `booking_pets` is readable when the joined booking is the caller's. `form_responses` pet ownership (the `pet_id` scope) is verified in the server action, not RLS — `pet_id` is only meaningful joined with the forced `client_id`. `authorizations`: client reads/inserts own, **append-only** (no update/delete grant).
- `booking_series`: client reads own; series rows created/updated by server actions + the series-roll cron under the service role (clients never write the rule directly). `client_debits`: client reads own; **admin/system write only** (debits and settlements move via admin actions, never client SQL).
- `inquiries`: **no public insert grant** — writes only via the service-role `submitInquiry` server action (honeypot + per-email rate-limit + Zod at the edge); signed-in clients read their own; admin reads and updates all.
- Public-read tables (`services`, `availability_windows`, `overnight_nights`): anon read; **every write is service-role**. `reviews`: anon read where `status='published'`; **no public insert grant** — the review form posts through the service-role `submitReview` action, which resolves identity from the session and caps how many one client may post (an insert grant made that cap decorative and left `author_name`/`body` attacker-controlled on a wall rendered into static HTML and JSON-LD). `settings`: authed read, service-role write.
- **Admin writes are service-role-only, by design.** Cal's admin surfaces never write with her own authenticated session: the tables above revoke writes from `authenticated` outright, so an admin session is refused at the grant before RLS is even consulted. The admin-write **policies** those tables used to carry were unreachable and have been dropped, because a policy standing on a revoked grant reads as though the write is allowed. Re-granting a write on any of them means restoring its policy in the same migration.
- **Grants are column-scoped, not just row-scoped.** RLS answers "is this the caller's row"; it never restricts which columns of an owned row the caller may name. So on `pets` and `profiles` the client `INSERT`/`UPDATE` grants list exactly the columns the client-facing actions write — `pets.photo_url`, for instance, is a storage path the server signs and republishes onto the public calendar, so a client grant would let it be pointed at any object in the bucket. `form_responses` is the **one remaining gap**: `authenticated` still holds a table-wide `UPDATE` on it, so `submitted_at` can be bumped over the REST API without the payload changing, which makes the owner-form freshness gate advisory rather than enforced. Revoking it waits on the paired code change that moves form writes to the service role. `profiles` has **no** client insert grant at all: self-serve rows come from the `handle_new_user` trigger and admin-created ones from `auth.admin.createUser()` firing the same trigger, so a grant there would only ever have been an attacker's way to mint `role='admin'` or a pre-approved `onboarding_status`.
- **Busy-range exposure (two trust levels).** Customer calendar reads busy ranges through a service-role server action projecting **only** start/end + pet thumbnails (species + signed photo URL) — **no owner name/id**, by construction (identity-free result type + a dedicated repo method). Admin calendar uses a separate **admin-gated** action joining owner + status for management. Pet photos live in a private bucket, served via short-lived signed URLs — intentionally client-visible (a photo is not a privacy concern); client identity is not.
- Admin (`role='admin'`) override expressed in each policy that a grant can still reach.
- **How these rules are tested.** There is no SQL test suite: the pgTAP extension the init migration installed was dropped once its `.sql` tests were gone (it was polluting the generated `Database` type with forty helper functions). Policies and grants are covered instead by the `*.integration.test.ts` suites, which run against the local Supabase stack with real clients — `npm run test:integration`, versus `npm run test:unit` for the pure logic. The generated schema types live in `src/lib/supabase/database.types.ts` (`npm run db:types`), and every repository or action parameter takes the `DbClient` alias rather than a bare `SupabaseClient`, whose defaulted schema generic would erase those types at the boundary.
- **Column-level guard (security).** The client `UPDATE` policy on `profiles` whitelists only self-editable columns. `role`, `lat`, `lng`, `kiche_allowed`, `onboarding_status`, `unclaimed`, `claimed_at`, and `invited_at` are **system/admin-set, never client-writable** (enforced by the allow-list column grant — new columns absent from the grant are non-client-writable automatically, no policy change) — otherwise a client could `SET role='admin'` and self-promote, `SET onboarding_status='approved'` and self-approve past the meet & greet, or self-flip `unclaimed` / forge `claimed_at`. Likewise clients never write `bookings.status` / `final_cents` / `payment_status` or `payments` rows by SQL; those move only through server actions and the Stripe webhook under the service role.

### Pre-created (unclaimed) clients

Cal can create a client record before the person signs up — to approve them, fill forms, and book on their behalf — via an **unclaimed shadow account**. `createUnclaimedClient` (admin-gated, service role) mints a real `auth.users` row with **no password**; the existing `handle_new_user` trigger creates the `profiles` row, which the action flags `unclaimed = true`. Every existing on-behalf flow (booking, forms, approval dropdown, RLS, exclusion constraint) is reused unchanged. Automated notifications are **suppressed while unclaimed** (`shouldNotify` predicate at each dispatch boundary — confirmation send + reminder cron); Cal handles comms manually. To migrate an offline client, Cal generates a one-time **claim link** (Supabase `recovery` `generateLink` — `invite` is rejected for an already-registered user, and these shadow accounts already exist; delivered by copy — never auto-emailed), which lands the client at `/claim` (via `/auth/callback?next=/claim`) to set a password; that clears `unclaimed` and stamps `claimed_at`, handing routing back to the `onboarding_status` gate. Email collision on create maps to a friendly "already exists" pointing at the existing client. Design: [spec](superpowers/specs/2026-06-24-admin-precreate-client-design.md).

**Assumptions & boundaries:**

- **Single provider.** One Cal; no `provider_id`. Adding helpers later is a multi-provider migration (thread `provider_id` through `availability_windows` + `bookings`).
- **Single timezone.** Store UTC; render `America/Denver` (Cal's region). Revisit only if Cal works across zones.
- **Cal tunes values, devs add types.** `/admin` edits rates, settings, and a service's configured amounts. Adding a new `pricing_type`, `concurrency` class, or service-specific form is a code change (closed enums + typed Zod) — by design, not a gap.

## Pricing model

> **The database is the source of truth for every rate.** This section describes the **model** — what kinds of rule exist, in what order they apply, and who may change them. It deliberately quotes **no amounts**: every one of them lives in a service's `pricing_config`, editable from `/admin/services`, and any number written here would be a second copy that rots. To read the live rates, read the config.

Pricing is **rule-based per service**, not flat. Each `services` row carries a `pricing_type` and a `pricing_config` — Zod-validated jsonb of the shape `{ modifiers, constraints }`. `modifiers` is an **ordered list over a closed union of rule kinds**; `constraints` is the booking limits that go with them (slot interval, min/max duration, dog cap, allowed species, soft distance warning).

A pure `features/pricing/quote()` evaluates that list against a flat `QuoteInput` and returns an itemized `QuoteBreakdown`. It does **not** branch on `pricing_type` — the config is the program, and the same evaluator runs every service. `pricing_type` remains the closed union that says which _kind_ of service this is (it decides the booking UI, the required forms, and which config schema validates), but adding a rate or changing one never touches code ([ENGINEERING.md](ENGINEERING.md) #5 pure logic, #4 config at edges).

**The rule kinds.** A base per night or per hour; per-unit add-ons, flat or tiered, where a "unit" is a species (the base covers the stay's first pet, dog → cat → other, so whichever species holds that spot bills one fewer); per-night toggles driven either by a condition or by a needy-pet ladder; per-hour opt-in add-ons; an allowance-then-per-unit line (used for travel miles and for exercise minutes beyond what the base includes); a percentage surcharge for premium days; a percentage discount; and a minimum floor. **Conditions** are a closed list too — always, no dogs, cats-only, any dog under six months, recurring series, stays over four or six nights — evaluated against server-derived facts, never client input. (Cats-only means at least one cat and no dogs; the plain "no dogs" test also holds for a stay with only a bird or a rabbit in it, which is not the household a cat-only label describes.)

**The seven phases**, applied in this fixed order, each line rounded to whole cents:

1. **Base** — per night or per hour.
2. **Per-unit add-ons** — extra pets, per-night toggles, opt-in hourly add-ons, exercise beyond the allowance.
3. **Premium-day surcharge** — a percentage of the running subtotal, either across the whole booking or pro-rated to the premium nights in it.
4. **Minimum floor** — tops a small booking up, before any discount.
5. **Automatic discounts** — every non-manual percentage discount whose condition holds, compounding.
6. **Manual discounts** — only those Cal has switched on for this booking.
7. **Travel** — per road mile beyond the free allowance, and **never discounted**.

Travel comes last on purpose, so it is not eroded by a discount meant for the service itself. The one exception is the **Complimentary** discount: a phase-6 discount cannot reach a line quoted after it, so the only way to a genuinely free booking is for the engine to leave the mileage line out, which it does when that discount is enabled. Result is persisted as `quote_breakdown` (the itemized lines) and `final_cents` (the total).

**Manual discounts — Cal's price adjustment.** A manual discount is an ordinary `pct_discount` in the config carrying `manual: true`, which means the engine applies it **only** when the booking's `enabledManualIds` names it. Cal toggles them from the booking's admin edit page; the enabled ids are written into the booking's frozen `quote_inputs`, so every later re-quote (an edit, a series roll) reproduces the same total. Turning one on re-quotes immediately, and if the client has already paid more than the new total, the overpayment is refunded through the payments adapter. They are also filtered out of the public `/services` rate breakdown, so an unadvertised kindness stays unadvertised — while the **client does** see the resulting line on their own booking. Two are seeded on every paid service (**Friends & Family** and **Complimentary**, per DECISIONS 4); house-sitting and walks also carry the older Kiche discount, and walks two behavior-based ones. Kiche keeps one extra rule the others do not: the booking's `kiche_welcome` consent flag (set by the client in the Details step, never affecting price) must be true before Cal can apply it. The per-account `profiles.kiche_allowed` flag is **deprecated** — retained, never read.

**Automatic discounts and surcharges** work the same way but need no admin action: their condition is derived server-side. The **recurring** discount is the notable one — it can only fire for a booking in a qualifying series, and the recurrence UI is off (see **Recurrence**), so in practice it does not fire at all today. Its rate lives in each service's `pricing_config`, not in `settings.recurring_discount_pct`.

**Service types.** The five `pricing_type`s are the real domain cases, not speculative abstraction: `house_sitting` (per night, multi-day date range), `check_in`, `walk` and `training` (per hour, single-day timeline), and `meet_greet` — **free**, `concurrency='exclusive'`, onboarding-only. The meet & greet is the required in-person introduction before a new client's first paid booking; it is **not publicly listed** (excluded from `/services`), is scheduled only inside the onboarding wizard, and has no public `/book/meet-greet`. See **Onboarding gate** under Route map.

**What `/admin/services` can and cannot edit.** The editor derives the **numeric leaves** of a config — amounts, percentages, free-unit allowances, tier values, and the numeric constraints — and renders them as dollar or number inputs; saving re-validates through the same Zod schema the engine parses with, and a legacy or unparseable config falls back to read-only rather than being overwritten. Adding, removing or relabelling a modifier, editing a condition, or changing the allowed species is deliberately **not** in the editor: those change what the rules _are_, and go through a migration.

## Booking state machine

Pure function `transition(state, event, ctx) → state | error` in `features/booking/` — no IO inside. **Quote is not a state**: distance + quote (`quote_breakdown` / `final_cents`) computed synchronously at submit. **Prepay is optional, decoupled from validity** — a booking is valid on _approval_, not payment; payment tracked on `payment_status`, can happen at booking (prepay) or later (amount-owed). **Reminder is not a state**: side-effect (Resend email N hours before a `confirmed` start; `reminder_sent_at` flag; SMS deferred).

**Mail is a side-effect too, and every send is gated.** The client gets a **received** acknowledgement when a booking is created and a **confirmation** on the transition to `confirmed`. Cal gets **admin alerts** — new booking request, new inquiry, client cancellation — addressed to the `ADMIN_NOTIFICATION_EMAIL` env var; with that unset, the alert path is a no-op that never constructs a mailer and never throws, so an unconfigured deploy is simply quiet. Nothing at all is sent to an **unclaimed** shadow account (see Pre-created clients). No send is allowed to fail a request: every dispatch logs and swallows.

```
submit ─┬ requires_approval? yes ─▶ pending_approval
        └ no  (auto-approve)  ─────▶ confirmed

pending_approval ── approve ──▶ confirmed
pending_approval ── decline ──▶ declined            (terminal)
confirmed ── end time reached ─▶ completed           (terminal, auto)
confirmed ── no-show (Cal marks) ─▶ no_show          (terminal; writes a client_debits row — CORE ONLY, no UI)
pending_approval | confirmed ── cancel ─▶ cancelled  (terminal; refund per policy below)
```

> **Three admin capabilities exist as tested cores with no interface**: marking a `confirmed` booking `no_show`, granting the remaining refund beyond the late-cancel tier, and settling a debit from the booking side. Each has a core, a server action and tests, but nothing on any admin page calls it, and `settings` no longer exposes the no-show percentage. They stay in the codebase because the transitions and the debit arithmetic are the tested part and the surfaces are cheap to add later. Read every mention of them below as **the model, not a live workflow**. (Debits themselves _are_ manageable — settle, waive, adjust — from the client detail page; that is a separate path.)

- `requires_approval` is **derived as the OR of three signals**: (1) the **distance** gate decision is manual (miles > `auto_approve_threshold_miles`); (2) the **time** gate decision is pending (`starts_at` beyond `auto_confirm_horizon_days` from now); (3) the service is flagged (`requires_approval`). A **refuse** from either gate (miles > `hard_cutoff_miles`, or beyond `hard_max_advance_days`) short-circuits the submit. Derivation is **per-occurrence** — a recurring series can straddle the time horizon (near occurrences auto-confirm, far ones pend; see Recurrence).
- **Slot held from submit onward** through any non-terminal state — no TTL, no expiry. Releases only on `declined` / `cancelled`.
- `completed` is automatic once end time passes (scheduled job).
- Stripe webhook is the **sole writer** of `payment_status` (a projection of `payments`); never changes `status`.
- **Manual discounts** applied by Cal (admin) → re-quote reduces `final_cents`; overpayment refunded if already prepaid (see Pricing model).
- **Client-initiated cancel** allowed, governed by the **cancellation / refund policy** below.
- Payment model is **deposit-ready**: a future mandatory-deposit + forfeit-on-late-cancel slots in via partial `payments` rows — no schema rework. MVP = prepay optional, full amount, **pay-later default**.

**Cancellation / refund policy** (all values Cal-tunable in `settings`):

- **Cutoff = `cancellation_full_refund_hours` (~48 h) before start.** Cancel **at or before** cutoff → **full** refund of whatever was paid (auto). Cancel **inside** cutoff → **`late_cancel_refund_pct`** (~50%) refund by default; granting the remaining refund is one of the cores-only capabilities above.
- **Refund issuance keeps the single-writer rule.** Cancel path **initiates** the refund through the `payments` adapter (`StripeGateway.refund`); the **Stripe webhook stays the sole writer of `payment_status`** (re-projects to `refunded` on `charge.refunded`). Cancel path never writes `payment_status` directly (#10).
- **Partial-refund state is modeled:** a full prepay that gets a `late_cancel_refund_pct` (~50%) refund leaves a `succeeded` `payments` row with `refunded_cents` set and projects to `partially_refunded` — the retained half is representable. (Was previously claimed impossible; corrected with SP4b's `refunded_cents` re-model.)
- **Debt gate.** Cancelling **unpaid inside the cutoff** (or a Cal-marked **no-show**) writes a `client_debits` row for what's owed (`late_cancel_refund_pct` / `no_show_charge_pct` of `final_cents`). An unpaid cancel **at/before** the cutoff owes nothing — free cancellation honored regardless of prepay. Any **unsettled** balance **blocks new bookings** until cleared (Cal marks settled offline, or client pays); gate checked **server-side** in the shared booking-artifacts path, so both quote preview and create call block. The series-roll cron also stops promoting a debtor's future occurrences.
- **No-show is a Cal admin action**, not automatic — the completion cron can't tell "no-showed" from "served, will pay later." `confirmed → no_show` (terminal) writes the debit. Cores only today, per the note above.

**Payments kill-switch.** Prepay ships behind `NEXT_PUBLIC_PAYMENTS_ENABLED`, **default off**, read through one helper that treats only the exact literal `"true"` as on, so a malformed value fails closed. With it off, the prepay CTA is hidden everywhere, `createPrepayIntent` early-returns, the Stripe webhook route 404s, and the confirmation email drops its prepay sentence — while balances still show as owed and the admin "Unpaid" pill stays. `NEXT_PUBLIC_*` is inlined at build time, so flipping it is a deploy, not a runtime toggle.

> **Operational rule: turn it off only while there are no live payment intents.** A 404-ing webhook is correct before launch, when no intent exists. Once intents are live, turning the flag off drops `payment_status.succeeded` and `charge.refunded` events on the floor — `refunded_cents` then never projects, and the class of over-refund bug that column exists to prevent comes straight back. Re-enable the flag **before** issuing any refund.

**In-place edit (mutation spine).** A non-terminal booking may be edited in place (time / pets / quantities / comments) via `editBookingCore`, parameterized by a `MutationPolicy` (client = all gates enforced; admin = warn-don't-block override, derived from the verified session role in the action layer, never the payload). Editing **re-quotes** (unpaid only — a paid booking locks price-affecting fields, returning `price_locked`) and **re-derives approval**, so a `confirmed` booking can return to `pending_approval`. A client may not self-edit inside the `cancellation_full_refund_hours` cutoff (mirrors the cancel-fee gate); admin overrides. Editing a series occurrence **detaches** it (`series_id → null`) and records its original cadence start in `booking_series.skipped_starts` so the roll cron never refills the slot. Service-swap is **not** an edit (cancel + rebook). Edit path **never touches Stripe**. _(Existing `rescheduleBookingCore` — time-only, price-preserving — retained for the meet-greet onboarding flow; unifying it under `editBookingCore` deferred so the onboarding gate doesn't reject a meet-greet reschedule.)_

## Recurrence

> **The recurrence UI is off.** `RECURRING_UI_ENABLED` (in `use-booking-scheduler.ts`) is `false`, and both create surfaces gate the recurrence step — and its step number — on it. Everything below is built, tested and dormant: the controls, the rule the submit path builds from them, the `booking_series` rows, the cron that materializes their occurrences, and the seeded recurring discount, which therefore cannot fire. Kept rather than retired by owner decision (DECISIONS 9); re-enabling it is flipping that one constant. Describe it as the model it is, not as something a client can reach today.

Engine is general (Google-Calendar-style); **MVP exposes weekly only**, with either a **fixed number of weeks** (`count`) or **open-ended** ("no end", `open_ended`). The booking system **never officially books past ~1 month** out:

- At submit, a `booking_series` row is written (rule + frozen `quote_inputs`); occurrences materialized only up to `recurrence_generation_horizon_days` (~42). Each occurrence's status derived per-occurrence (see Booking state machine): within `auto_confirm_horizon_days` → `confirmed`; beyond → `pending_approval`.
- A daily **series-roll cron** (sibling of the reminder / completion crons) does two jobs: **promote** `pending_approval` occurrences to `confirmed` as they cross into the confirm horizon (re-checking availability + the no-overlap constraint; a now-conflicting slot stays pending and is flagged for Cal, never silently dropped), and **extend** open-ended series by materializing newly-in-horizon occurrences. Skips a debtor's occurrences (see cancellation/refund debt gate).
- This single horizon mechanism also covers **far one-off bookings**: a booking beyond the confirm horizon sits `pending_approval`, auto-confirms when it enters the horizon (Cal can decline during the window).

- **Booking flow** — one booking per submit at MVP (no multi-item cart).
- **Booking rules** — hours 6:30am–10:00pm (start & end within), min lead time unchanged, advance → soft `auto_confirm_horizon_days` (~1 month; beyond → pending, not refused) with a `hard_max_advance_days` sanity cap. Tunable.
- **Reminder timing** — 24 h before a confirmed start (`reminder_lead_hours`). Tunable.
- **Prepay** — full amount, **pay-later default**, prepay optional, and shipped behind the payments kill-switch until Cal's Stripe account is live.
- **Cancellation / refund** — full refund ≥48 h out; <48 h → 50%; unpaid late cancel / no-show → debt that blocks re-booking until settled. Values tunable (Booking state machine).
- **Recurrence breadth** — weekly only at MVP; fixed week-count **or** open-ended via the rolling ~1-month materialization horizon (Recurrence). Kept behind its flag by owner decision.
- **House-sitting travel** — a house-sit bills travel like every other service: per road mile past a free allowance, configured on the service.
- **Per-pet fields** — the pet-scoped `pet_care` profile covers meds / feeding / behavior; vet contact lives on the `owner` form. Only `birthdate` earned a column, because pricing reads it.

### Intake profiles & the booking requirement gate

Cal's service-shaped intake forms are **normalized into five reusable profiles** rather than re-collected per booking. Each is a `form_responses` row keyed by `form_key` + scope (see Data model). `FORMS.md` (repo root) is Cal's raw, owner-written source; it is requirements to normalize, not a schema.

**Five active form keys:**

| Key            | Scope                 | Description                                                                                                                                                                                                                    |
| -------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `owner`        | account               | Identity, pronouns, backup and second-owner contacts, emergency contacts, **and the household vet's name and phone**; also where the expense-authorization e-sign is prompted (the acceptance itself goes to `authorizations`) |
| `home_access`  | account               | Door codes, alarms, wifi, parking                                                                                                                                                                                              |
| `home_sitting` | account               | Sleeping arrangements, house rules, guest policy                                                                                                                                                                               |
| `pet_care`     | per-pet               | Medical, behavior, feeding, exercise                                                                                                                                                                                           |
| `pet_walk`     | per-pet, **dog-only** | Route, leash, off-leash — species-gated in the manifest                                                                                                                                                                        |

Legacy keys: `emergency` is **render-only** — still registered so an old row validates and displays (in admin, where Cal may need to read one), but nothing writes it any more, it is not a required profile, and it is not offered on the profiles page. `owner` superseded it. `home`/`pet` are retired outright.

**Signup collects the profile and nothing else.** The meet & greet requires **zero** forms (DECISIONS 1): it is the free introductory visit that comes _before_ any intake, and requiring a profile there would dead-end every self-serve signup, because the owner form is only reachable once Cal has approved the account — which only happens after the visit. Emergency contact and vet details therefore live on the `owner` form, required at the first **paid** booking.

**Pet-aware services.** `house_sitting`, `walk`, `check_in`, and `training` are all pet-aware (they accept assigned pets from the client's profile). Only `house_sitting` and `walk` price by pet headcount; `check_in` and `training` are hours-only. `training` accepts a single dog (`max_pets = 1`).

**Requirement manifest (code, not schema).** `REQUIRED_PROFILES` in `src/features/booking/required-profiles.ts` maps `pricing_type` → required forms: `house_sitting` → [owner, home_access, home_sitting, pet_care, pet_walk(dog)]; `check_in` → [owner, home_access, pet_care, pet_walk(dog)]; `walk` → [owner, pet_care, pet_walk(dog)]; `training` → [owner, pet_care]; `meet_greet` → **[]** (deliberately empty, for the reason above). `pet_walk` carries an explicit `species: "dog"` predicate — only dog-assigned pets trigger it. Kept in code so Cal can't misconfigure required forms; `services.form_key` is vestigial and no longer consulted by the gate.

**Hard-block gate.** Pure `bookingRequirements(...)` returns per-profile `complete | stale | missing`; `computeBookingArtifacts` blocks a client-policy booking (`profiles_incomplete`) until every required profile is satisfied. **Stale** = `submitted_at` older than `FRESHNESS_WINDOW_DAYS` (180); a one-click **"Confirm up to date"** bumps `submitted_at` without re-entering data. **Missing** = no row. A pet requirement is per-assigned-pet and vacuous when no pets are on the booking (pet selection is enforced separately by quantity validation). Admin-on-behalf policy warns instead of blocking. Clients complete/confirm profiles inline from the booking flow's requirements checklist or standalone at `/account/forms`; Cal can complete on a client's behalf from the admin client detail.

## Copy placeholders

> Filling these in is governed by the **copy-sync protocol** ([docs/CONTENT.md](CONTENT.md)): Cal's verbatim text captured in `docs/content/cal-source.md`, tracked in `docs/content/copy-ledger.md`, rendered from `src/content/marketing.ts`. This section remains the marker-grammar reference.

`src/content/` holds the other Cal-owned registries beside it: `references.ts` (each client reference's name, an optional pet photo, and the **published-contact consent** that decides whether the chip opens their details or routes the visitor to the contact form — the list renders nothing at all while it is empty), `rover-reviews.ts` (imported testimonials, reconciled into the DB by the sync script), and `socials.ts`.

Marketing copy Cal must write is stubbed with double-square-bracket markers. Keep structure in code; Cal owns voice + substantive claims.

- **Marker:** `[[ ... ]]`. Grep with `rg "\[\["`.
- **Forms:**
  - `[[HEADER: purpose]]` — section/card/page header
  - `[[BODY: what this paragraph should cover]]` — paragraph copy
  - `[[Item N: what it is]]` — list/card/FAQ/resource stub
- **Header rules:** basic, descriptive noun phrases. No first-person, no quirky/pushy phrasing. ✗ "Pricing flexibility matters to me." → ✓ "Sliding cost scale". If unsure, write `[[HEADER: purpose]]`. (POV note below is about body prose, not headers.)
- **Body rules:** describe purpose only. No invented service claims, philosophy, or biographical detail — Cal supplies all of that.
- **Point of view (POV) — load-bearing.** Two registers, by surface:
  - **Marketing body copy = Cal's first person.** Everything in `src/content/marketing.ts` (home, about, services, reviews, resources, gallery, contact intro/FAQ, long-form service detail) speaks as Cal: "I've cared for hundreds of animals", "I usually reply within a day". This is Cal's voice; never describe Cal in third person here.
  - **Non-marketing / system text = third person about Cal.** Booking flow, account, onboarding, admin, toasts, errors, status lines, quote panels, form hints — refer to Cal in third person: "Cal will get back to you", "pending Cal's approval", "contact Cal", "Notes for Cal". This text is the system speaking to the client, not Cal.
  - **Exceptions (intentional, do not "fix"):** (1) **Client-signed consent** stays the _client's_ first person — `EXPENSE_AUTH_TEXT` ("I authorize Cal to seek veterinary treatment…") is the client speaking, correct as-is. (2) **Signed correspondence** — the confirmation and reminder emails are personal letters signed "— Cal Barba", so Cal's first person is allowed there ("I refund you in full"). The exception is the **signature**, not the medium: the unsigned system mail (the received acknowledgement, and the admin alerts about a new request, a new inquiry, or a client cancellation) is third person about Cal like every other system surface.
- **Example items:** for resource/FAQ/testimonial arrays, always use stubs (`[[Resource 1: name]]`); never invent examples.
- **Locations:** Colorado only. No towns/cities/neighborhoods in copy, alt text, or addresses.
- **Don't assume Cal's services or audience-facing voice** — overnight stays, meet-and-greets, cat care, medication handling, sliding-scale philosophy, background, etc. all placeholdered until Cal confirms.
- **Public emergency resources** (ASPCA poison line, 24/7 vet ER) OK as real entries — verifiable, not a claim about Cal. **Generic local resources** (humane society, dog park) → stub.

## Deliberately dormant

Things that look unfinished on a read-through but are decisions. Each is one small change away from live; none of them should be "fixed" without asking.

- **Dark mode is latent.** The full dark palette exists in `globals.css` under a `.dark` variant, but nothing adds that class — there is no theme toggle and no `prefers-color-scheme` wiring — so no visitor sees it. The tokens are maintained alongside the light ones so the day a toggle lands, it works. Keeping them is cheaper than re-deriving a warm dark palette later.
- **`telephone`, `sameAs` and the social links are empty on purpose.** The structured-data business record omits `telephone` and `sameAs`, and `src/content/socials.ts` holds empty strings, because Cal has no public phone number or profiles to publish yet. An empty entry renders **nothing** rather than a dead `#` link; filling one in is the whole change.
- **The gallery shares one alt text.** Every photo carries the same generic description. Individually written alt text is Cal's to supply, and a wrong-but-specific description is worse than an honest generic one.
- **The recurrence UI and three admin capabilities are built but unreachable** — see **Recurrence** and the note under **Booking state machine**.
